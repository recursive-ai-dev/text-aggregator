# Code Quality Audit Report

## 1. Affine Memory Accounting Bypass Leads to OOM
- **File(s) and line numbers:** `text_aggregator.py`, lines 691-695 (`_bounded_read`) and 1019-1028 (`Processor.run`).
- **The specific problem:** The `_bounded_read` context manager releases its memory budget immediately when file extraction finishes. However, the extracted `FileRecord` (containing the full string and chunks in memory) is stored in the `DeterministicExecutor`'s out-of-order queue until earlier files complete.
- **Why it matters:** If one large file takes a long time to process, fast subsequent files will pile up in the executor's results dictionary. Because their budgets were prematurely released, the system continues allocating new reads, silently bypassing the 512MB hard limit and causing an Out-Of-Memory (OOM) crash on large repositories.
- **The proposed fix:** Add a `size: int = 0` field to `FileRecord` to store the file size. Remove the `self.budget.release(size)` call from the `finally` block of `_bounded_read`. Instead, in `Processor.run`, explicitly release the memory (`with self.engine._budget_lock: self.engine.budget = self.engine.budget.release(record.size)`) *after* `self.builder.write_file(record)` has executed and the record is ready for garbage collection.
- **Overlap:** None.

## 2. Unhandled Thread Exceptions Cause Main Loop Deadlock
- **File(s) and line numbers:** `text_aggregator.py`, lines 437-442.
- **The specific problem:** The `wrapper` function in `DeterministicExecutor.submit` executes the thread worker payload (`fn(*args)`) without a `try...finally` block. If the payload raises an unhandled exception (e.g., `MemoryError`, decoding failure), the event flag is never set.
- **Why it matters:** The main thread in `drain_ordered` polls tasks sequentially by their `event_id`. If any task crashes, `drain_ordered` will infinitely wait for that task's event, causing a complete application deadlock instead of failing gracefully.
- **The proposed fix:** Wrap `result = fn(*args)` in a `try...except BaseException as e: result = e` block, and move the dictionary assignment (`self._results[event_id] = result`) and `self._event.set()` into a `finally` block to guarantee signaling.
- **Overlap:** Modifies `DeterministicExecutor.submit` (logically relates to Item #6, but touches different lines).

## 3. Silent Data Loss on Duplicate/Checkpointed Files
- **File(s) and line numbers:** `text_aggregator.py`, lines 708-725 and 816-835.
- **The specific problem:** If a file was processed in a previous run or is an exact duplicate, the engine returns a dummy record with `error="CHECKPOINTED"` or `"DUPLICATE"`. In `AttestedBuilder.write_file`, this error bypasses the `if not record.error:` block, meaning the content is intentionally omitted from the output.
- **Why it matters:** Running the tool twice on the same repository will result in an empty output document the second time, and duplicated files (e.g., empty `__init__.py` files) will be missing entirely. The output document state desyncs from the actual file system, breaking the core feature of the tool.
- **The proposed fix:** Remove the early return `_dup_record` logic completely. Always decode the file content and return a fully populated `FileRecord`. Only use the `is_processed` and `seen_hashes` flags to dynamically filter out redundant insertions into `new_chunks` and the SQLite DB.
- **Overlap:** None.

## 4. Invalid Merkle Tree Inclusion Proofs
- **File(s) and line numbers:** `text_aggregator.py`, lines 519-546.
- **The specific problem:** `MerkleTree.audit_path` traverses the tree from root to leaf, appending sibling hashes to the `proof` array in that top-down order. However, the `verify` function strictly expects the proof array to be ordered bottom-up (from the leaf hashing upwards to the root).
- **Why it matters:** Every cryptographic inclusion proof generated by the tool will fail verification (`verify` will always return `False`), rendering the primary attestation feature useless.
- **The proposed fix:** Reverse the `proof` list right before caching and returning it in `audit_path` (e.g., call `proof.reverse()`), ensuring the siblings are ordered correctly from leaf to root.
- **Overlap:** None.

## 5. SQLite Transaction Leaks & Single-Insert Overhead
- **File(s) and line numbers:** `text_aggregator.py`, lines 643-666.
- **The specific problem:** `CheckpointManager.record` executes multiple `conn.execute()` statements followed by a manual `conn.commit()`. If any SQL statement fails, the transaction is left open indefinitely. Furthermore, it inserts CDC chunks one-by-one using a Python `for` loop inside the global write lock.
- **Why it matters:** Transaction leaks corrupt subsequent writes by the same thread, breaking ACID guarantees. The single-row loop creates massive Python-to-SQLite context switch overhead, heavily degrading throughput for large files containing thousands of chunks.
- **The proposed fix:** Replace the manual commit with a connection context manager (`with conn:`). Replace the `for chunk_hash, _ in record.chunks:` loop with a single `conn.executemany("INSERT...", ((h, record.content_hash) for h, _ in record.chunks))` call.
- **Overlap:** None.

## 6. Event Race Condition Creates CPU Busy-Wait
- **File(s) and line numbers:** `text_aggregator.py`, lines 450-459.
- **The specific problem:** In `drain_ordered`, `self._event.clear()` is called entirely outside the thread lock immediately after `wait()` times out. If a worker thread finishes and calls `self._event.set()` precisely at this moment, the event is incorrectly cleared and the notification is lost.
- **Why it matters:** Because events are randomly lost, the system relies on a `timeout=0.1` fallback to avoid deadlocking. This degrades the main thread into a CPU-burning busy-wait loop that pointlessly polls state 10 times a second.
- **The proposed fix:** Move `self._event.clear()` inside the `with self._lock:` block, calling it only when `next_id` is missing from `self._results`. Then change `self._event.wait(timeout=0.1)` to `self._event.wait()` (no timeout), safely eliminating the polling behavior.
- **Overlap:** Modifies `DeterministicExecutor.drain_ordered` (logically relates to Item #2).

## 7. Gitignore Global Traversal of Excluded Folders
- **File(s) and line numbers:** `text_aggregator.py`, line 141.
- **The specific problem:** The `_load_gitignores` method uses `self.root.rglob(".gitignore")` to discover ignore rules upfront. This blindly traverses the entire directory tree, entirely ignoring the `DEFAULT_IGNORE_PATTERNS` that exclude directories like `node_modules` or `.git`.
- **Why it matters:** On large web or Rust projects, this causes massive startup I/O lag from traversing blacklisted dependency directories. Worse, a `.gitignore` inside a dependency will erroneously apply its custom ignore rules to the user's global repository scan.
- **The proposed fix:** Remove the `_load_gitignores` pre-pass using `rglob`. Instead, dynamically discover and load `.gitignore` files inside the `os.walk` loop of `Processor._collect_files` *after* ignored directories have been cleanly pruned from `dirs[:]`.
- **Overlap:** None.

## 8. Gitignore Anchored Wildcard Matching Broken
- **File(s) and line numbers:** `text_aggregator.py`, lines 198-201.
- **The specific problem:** For anchored gitignore rules, `_match` artificially truncates the incoming path array to the length of the pattern array (`path_parts[: len(check)]`). This permanently breaks patterns containing the `**` wildcard, which legally match an arbitrary number of path components.
- **Why it matters:** Anchored `.gitignore` rules with wildcards like `/**/*.log` or `/build/**/*.txt` will fail to match deeply nested files because the path is truncated before the recursive `**` evaluation can process all directories, causing false negatives (accidental inclusion of ignored files).
- **The proposed fix:** Remove the `len(check) > len(path_parts)` check and slicing entirely. Change the logic to pass the full `path_parts` array to `_match_components` so the depth-first search can correctly evaluate `**` depths.
- **Overlap:** Modifies `GitignoreMatcher._match`, but touches different lines than Item #7.

## 9. Binary File Corruption via latin-1 Fallback
- **File(s) and line numbers:** `text_aggregator.py`, lines 756-763.
- **The specific problem:** The `_decode` method blindly falls back to `latin-1` for any file that fails UTF-8 decoding, lacking any binary file detection.
- **Why it matters:** If a user specifies `--all-ext` or targets folders containing binary files (e.g., images, `.so`), the tool will decode megabytes of binary noise as `latin-1` text, corrupt the output file with garbage, and burn significant CPU executing regex word counts (`re.findall(r"\w+")`) over raw binary data.
- **The proposed fix:** Remove the `latin-1` fallback. If UTF-8 decoding fails, check for binary data (e.g., `b'\x00' in raw`). If binary, return a `FileRecord` with `error="BINARY_FILE"` so the file is explicitly skipped and cleanly logged.
- **Overlap:** None.

## 10. Cross-Device Link Crash on Finalization
- **File(s) and line numbers:** `text_aggregator.py`, line 862.
- **The specific problem:** `AttestedBuilder.finalize` uses `os.replace(self.spool_path, self.output_path)` to move the output file from `/tmp` to its final destination.
- **Why it matters:** On Unix systems where `/tmp` is mounted on a different filesystem or partition (e.g., `tmpfs`) than the destination directory, `os.replace` will crash immediately with `OSError: [Errno 18] Invalid cross-device link`, destroying the user's aggregated data at the very end of the run.
- **The proposed fix:** Import the `shutil` module and replace `os.replace` with `shutil.move(self.spool_path, self.output_path)`, which safely handles cross-filesystem boundaries by automatically falling back to copy-and-delete.
- **Overlap:** None.

## 11. SQLite Schema Incompatibility with Older Environments
- **File(s) and line numbers:** `text_aggregator.py`, line 610.
- **The specific problem:** The database schema sets `timestamp REAL DEFAULT (unixepoch())`. The `unixepoch()` SQL function was only introduced in SQLite 3.38.0 (2022).
- **Why it matters:** On operating systems with older SQLite libraries (which are common in Python 3.9 environments, as officially required by the README), the application will crash instantly with a `sqlite3.OperationalError` during initialization.
- **The proposed fix:** Replace `unixepoch()` with `(CAST(strftime('%s', 'now') AS REAL))` to ensure backwards compatibility across all active SQLite 3 versions.
- **Overlap:** None.

## 12. Unlinked Temporary Spool File Leaks on Interrupt/Crash
- **File(s) and line numbers:** `text_aggregator.py`, lines 796-797 and 1180-1185.
- **The specific problem:** `AttestedBuilder` opens a temporary file (`agg_<pid>.tmp`) in `/tmp`, but there is no `finally` block or `atexit` handler to clean it up if the program crashes, raises an exception, or receives a SIGINT.
- **Why it matters:** Every interrupted or crashed run of the aggregator will leak a potentially massive temporary text file in the system's `/tmp` directory, eventually causing silent disk space exhaustion.
- **The proposed fix:** Wrap the core execution pipeline in `main()` or `Processor.run()` with a `try...finally:` block that checks if `os.path.exists(processor.builder.spool_path)` and calls `os.unlink()` to ensure the temporary output file is deleted on exit.
- **Overlap:** None.

## 13. SIGINT Handler Hangs on Large Repositories
- **File(s) and line numbers:** `text_aggregator.py`, lines 1180-1183.
- **The specific problem:** The signal handler calls `processor.executor.shutdown()`, which defaults to `wait=True` and `cancel_futures=False`. Because `Processor` enqueues all files upfront, shutting down blocks the main thread until the entire active queue is completely processed.
- **Why it matters:** Users pressing `Ctrl+C` expect the program to stop immediately. Instead, it prints "shutting down..." and stubbornly continues processing potentially thousands of files, resulting in poor UX and loss of control.
- **The proposed fix:** Update the call to `processor.executor.shutdown(wait=False, cancel_futures=True)` to immediately cancel pending work and exit cleanly.
- **Overlap:** None.

## 14. Determinism Violated by Output File Timestamp
- **File(s) and line numbers:** `text_aggregator.py`, line 805.
- **The specific problem:** `AttestedBuilder.write_header` embeds `datetime.now().isoformat()` directly into the header of the aggregated output file.
- **Why it matters:** This natively violates the system's core "Determinism Guarantee" advertised in the README. Running the tool twice on the exact same codebase will produce byte-for-byte different files, defeating external caching, ruining reproducible builds, and generating noisy Git diffs.
- **The proposed fix:** Remove the timestamp from the output file entirely, or allow passing a static deterministic timestamp via standard CI environment variables like `SOURCE_DATE_EPOCH`.
- **Overlap:** None.

## 15. Massive CPU/Memory Overhead via Nested `lru_cache`
- **File(s) and line numbers:** `text_aggregator.py`, lines 212-214 and 237-239.
- **The specific problem:** The `_match_components` and `_match_glob` methods decorate their inner recursive functions (`dfs`) with `@functools.lru_cache(maxsize=None)`. Because the inner function is recreated on every method call, a new cache object and lock are instantiated and immediately garbage collected thousands of times during traversal.
- **Why it matters:** This causes severe redundant memory allocation and CPU overhead, heavily degrading directory traversal speeds on large codebases while providing zero cross-call caching benefits.
- **The proposed fix:** Remove the `@functools.lru_cache` decorators. Instead, initialize a simple dictionary (`memo = {}`) outside the inner `dfs` function and manually perform lookups and cache assignments inside `dfs` to avoid excessive instantiation overhead.
- **Overlap:** None.

## 16. Curses Mode Swallows Fatal Errors (Returns Exit Code 0)
- **File(s) and line numbers:** `text_aggregator.py`, lines 1058 and 1188-1190.
- **The specific problem:** When running in Curses UI mode, if a fatal exception occurs, `screen_process` catches it and returns an error tuple `("error", {...})`. The `main` function simply prints this tuple and exits naturally with a successful `0` status code.
- **Why it matters:** If the tool fails when executed in a CI/CD pipeline or automated shell script where a TTY is allocated, the shell will silently assume success (exit code 0), allowing broken deployments or missing code bundles to pass securely.
- **The proposed fix:** In `main()`, inspect the tuple returned by `curses.wrapper()`. If it indicates an error (e.g., `result[0] == "error"`), explicitly call `sys.exit(1)`.
- **Overlap:** None.

## 17. Dead Code Architectural Claims
- **File(s) and line numbers:** `text_aggregator.py`, lines 289-314 and 386-416.
- **The specific problem:** The `MemoryArena` class for zero-copy buffering, and the `LamportClock` / `CausalEvent` components for deterministic happens-before ordering, are defined but completely orphaned. They are never instantiated or invoked anywhere in the active execution path.
- **Why it matters:** They add significant cognitive load and create misleading structural claims (e.g., the README heavily emphasizes Lamport Clocks for determinism, whereas the actual determinism simply relies on sorting an integer counter in a thread lock).
- **The proposed fix:** Delete the `MemoryArena`, `LamportClock`, and `CausalEvent` classes completely to clean up the codebase and accurately reflect true runtime behavior.
- **Overlap:** None.
